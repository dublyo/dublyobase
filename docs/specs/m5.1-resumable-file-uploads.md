# M5.1 Spec: Resumable File Uploads

Status: implemented in v0.6.1
Depends on: v0.6.0

M5.1 extends local file storage with Dublyobase-native resumable uploads. It is
designed to make large files reliable behind public proxies that may close a
single long request after about 60 seconds.

## Goal

Let clients upload large files in retry-safe chunks, then complete the session
into the same protected file metadata used by the existing M5 multipart upload.

Success means:

- Clients can create a durable upload session for a record file field.
- Clients can upload chunks independently and retry failed chunks.
- Upload session metadata is stored in Postgres.
- Chunk bytes live on local disk until completion or cancellation.
- Completion assembles one original file and updates the record file field.
- Completion returns the updated record, matching the existing multipart route.
- Abandoned sessions expire after 24 hours and can be explicitly canceled.

## Scope

In scope:

- Local storage only.
- Native Dublyobase resumable protocol.
- Database-backed session and chunk metadata.
- Chunks stored under a temporary local upload namespace.
- Optional per-chunk SHA-256 checksum validation.
- Optional final SHA-256 checksum validation.
- Replace and append upload modes.
- Explicit cancel endpoint.
- Integration tests for resume, checksums, completion, and cleanup.

Out of scope:

- Tus compatibility.
- S3/R2 multipart uploads.
- Browser admin UI uploader.
- Virus scanning.
- Background worker scheduling.
- Cross-instance distributed file locking.

## User Flow

1. Client creates a normal record.
2. Client starts an upload session for a file field with filename, total size,
   chunk size, mode, and optional final checksum.
3. Client sends chunks with `PUT` by zero-based chunk index.
4. Dublyobase writes each chunk to local temp storage and records chunk metadata
   in Postgres.
5. Client retries missing or failed chunks as needed.
6. Client completes the session.
7. Dublyobase verifies all chunks are present, assembles the original file,
   optionally validates the final checksum, updates the record file field, and
   removes temporary chunks.
8. Downloads continue to use the existing protected file-token route.

## Requirements

- Session TTL is 24 hours.
- Session state survives process restarts.
- Chunk files are never written using trusted client filenames.
- Upload IDs and file IDs are server-generated UUIDs.
- `MAX_UPLOAD_MB` still caps total file size.
- `totalChunks` must be bounded to prevent tiny-chunk abuse.
- Single-file fields reject append mode.
- Multiple-file fields accept replace and append mode.
- Missing chunks prevent completion.
- Repeated chunk uploads replace that chunk while the session is open.
- Completion marks the session as completing to prevent double completion.
- Completion returns the updated record JSON.
- Canceling a session removes temporary chunk files.

## Frontend

No admin UI change in M5.1. Browser and SDK clients can build resumable upload
flows on top of the HTTP API. The future admin panel can reuse this protocol for
large file fields.

## Backend

Main files:

- `core/file_uploads.go`: upload session lifecycle, chunk storage, assembly,
  checksums, cleanup.
- `apis/file_uploads.go`: HTTP handlers for create, chunk, complete, cancel.
- `core/migrations/0006_file_upload_sessions.sql`: durable session metadata.
- `apis/serve.go`: route wiring.
- `apis/middleware.go`: CORS support for the checksum header.

## Database

New control-plane tables:

```sql
_dbo.file_upload_sessions
_dbo.file_upload_chunks
```

Sessions store the project, collection, record, field, generated file ID,
filename, mode, total size, chunk size, status, actor scope, and expiry.

Chunks store one row per uploaded chunk index with size and server-computed
checksum.

## APIs

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/api/projects/{slug}/files/{collection}/{recordId}/{field}/uploads` | Create upload session |
| `PUT` | `/api/projects/{slug}/files/uploads/{uploadId}/chunks/{index}` | Upload one raw chunk |
| `POST` | `/api/projects/{slug}/files/uploads/{uploadId}/complete` | Assemble chunks and update record |
| `DELETE` | `/api/projects/{slug}/files/uploads/{uploadId}` | Cancel upload session |

Create body:

```json
{
  "filename": "video.mp4",
  "size": 52428800,
  "chunkSize": 1048576,
  "mode": "replace",
  "checksumSha256": "optional-final-sha256"
}
```

Chunk uploads may include:

```http
X-Checksum-SHA256: optional-chunk-sha256
```

Complete body:

```json
{
  "checksumSha256": "optional-final-sha256"
}
```

## UI/UX

The API supports client progress UIs by returning `totalChunks`, `chunkSize`,
`expiresAt`, and per-chunk `size`/`checksumSha256`. Clients can resume by
keeping the upload ID and retrying failed chunk indexes.

## Edge Cases

- Unknown project, collection, record, or file field.
- Upload session expired or canceled.
- Chunk index outside `0..totalChunks-1`.
- Chunk body size does not match expected size.
- Chunk checksum header does not match bytes.
- Final checksum does not match assembled bytes.
- Completion attempted before all chunks are uploaded.
- Record is deleted after session creation.
- Update rule changes after chunks are uploaded.
- Process restarts between chunk uploads.

## Security

- Every endpoint resolves project record auth.
- Session creation verifies the caller has update access to the target record.
- Non-service callers can continue only sessions created under the same actor
  scope; upload IDs are not enough when a bearer identity changes.
- Storage paths are built from safe server-generated segments.
- Client filenames are stored as display metadata only.
- Checksums are never trusted; they are recomputed server-side.
- Temporary upload files are isolated under `_uploads`.
